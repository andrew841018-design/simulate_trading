3. FastAPI 到底怎麼把資料送進 function

看不到手寫 create_order(order=...)，是因為 framework 依宣告建立參數 dictionary，再做 keyword expansion。

CURRENT

  2. Sender 建立 HTTP requestTestClient 的 .post(..., json=..., headers=...) 將 dictionary 編碼成 body/header；真實 UI 未來也會做同一件事。

  6. 回程handler return 的 Python object 經 FastAPI JSON encoding 變成 HTTP response；client 的 response.json() 再解析回 Python object。

TestClient 與真實網路的差別

5. Flow B — GET /v1/accounts/{account_id}

一個 path parameter 經 FastAPI 進 handler，再用 parameterized SQL 讀 stored values，最後計算 derived value。

CURRENT

  2. Router compositionmain.py prefix /v1/accounts + accounts.py path /{account_id} → full path。
  3. Path bindingFastAPI 將 URL segment SIM-001 綁到 function parameter account_id: str。
  4. Dependency bindingDepends(get_account_connection) 產生 connection。Production 用 runtime DSN；API test 用 override 的 test connection。
  5. DB requestget_account 將 account_id 放進參數 tuple (account_id,)，送給 psycopg 執行 SELECT total_cash, reserved_cash FROM accounts WHERE account_id = %s。

6. Flow C — POST /v1/orders

已驗收的LIMIT BUY流程；SELL仍缺少核准的持倉預留語意。

CURRENT CODE
  1. 輸入CreateOrderRequest接收account_id、action、order_type、quantity、price、symbol；Idempotency-Key經header綁定。嚴格型別／精度與其他未落地限制見spec。
  2. 本地準備order_request_payload=model_dump()，price格式化為兩位小數字串；order_id=str(uuid4())。生成UUID不代表訂單已成立。
  3. 交易開始with connection.transaction()包含後续查詢、資金變動及五表寫入。
  4. 既有key從idempotency_requests讀saved_payload、saved_response、saved_status；同payload回保存結果，不同payload回409。已保存201才是目前已驗收的重播範圍；pending與並行首次使用仍待後續处理。
  5. 新key建立pending row；SELECT total_cash, reserved_cash FROM accounts WHERE account_id=%s FOR UPDATE，查不到帳戶回404並回滾新寫入。
  6. 資金判斷required_cash=quantity×price；available_cash=total_cash-reserved_cash。不足回409並回滾；足夠則增加reserved_cash。
  7. 保存新單INSERT orders後，建立version1、NULL→OPEN、ORDER_CREATED transition；初始payload是六個request欄位加fill_quantity=0。
  8. 同交易outbox以相同transition_payload建立outbox event；event_id另由uuid4產生，並关联order_id／status_change_version。
  9. 保存回應response_body是六個request欄位加order_id，保存response_status=201與completed_at，再return response_body。
  10. 交易退出無既有外層交易時成功退出context會提交；目前API fixture已有外層交易，所以內層是savepoint，最後由fixture rollback。例外會撤銷本次交易／savepoint內的效果。

INSERT位置對應

orders SQL與Python tuple的順序都是：order_id, account_id, action, order_type, quantity, price, symbol。不是依字典欄位名稱自動配對。其餘orders欄位由DB default提供。

回應與查詢分工

POST response_body共7欄，沒有status、fill_quantity或account現金。GET /v1/orders/{order_id}透過orders JOIN accounts讀取order_id、status、fill_quantity及account四欄：account_id、total_cash、reserved_cash、available_cash。

未知帳戶404、不足資金409、schema422不保存idempotency結果；成功201才保存。同key不同payload的409不覆寫原成功紀錄。

驗證界線已完成初始BUY、拒絕／重試、重播／衝突、初始事件與一個outbox失敗回滾。尚不能由這些證據宣稱SELL、fill/cancel、並行key競爭、跨連線durability或Kafka已完成。

9. Config、connection、migration、seed 的資料流

Runtime request connection 與 Alembic migration connection 是兩條不同入口。

RUNTIME CONNECTION
  1. app/config.py 建立 account_settings
  2. 環境／ignored .env 提供 DATABASE_URL
  3. app/database.py 呼叫 psycopg.connect()
  4. dependency yield connection 給 handler
  5. handler 完成後 finally close
ALEMBIC CONNECTION
  1. alembic.ini 定義 script location / default SQLAlchemy URL
  2. migrations/env.py 依 mode 呼叫 run_migrations_offline() 或 run_migrations_online()
  3. run_migrations_online() 用 engine_from_config 建 connection；offline 只用 URL 輸出 SQL
  4. revision upgrade() 送 DDL
  5. Alembic transaction 寫 revision

Test DB upgrade 特殊路徑

  1. Sourcescripts/upgrade_test_database.py 讀 TEST_DATABASE_URL。
  2. Fail-close guard解析 URL 後 assert database name ends _test。
  3. Transformdriver name 轉為 postgresql+psycopg，寫入 in-memory Alembic config。
  4. Receivercommand.upgrade(config, "head") 觸發 migrations/env.py 與 revision chain。

Deterministic account seed

scripts/seed_accounts.sql 是 SQL artifact，不會被 FastAPI 自動執行。執行者必須用 psql/DB tool 主動送出；ON CONFLICT(account_id) DO UPDATE 讓同一 seed 可重跑，固定 SIM-001 / 100000.00 / 30000.00。

兩個 URL source 不同Runtime app 的 DB URL 由 AccountSettings 提供；一般 Alembic 預設 URL 在 alembic.ini。Test upgrade script 才會主動用 TEST_DATABASE_URL 覆寫 Alembic config。

15. 你拿任何變數追問時，固定用這條鏈回答

避免只回答「FastAPI 自動做」或「從 request 來」這種不完整說法。

1. Birth

在哪個 request/path/header、DB row、default、fixture、local expression 出生？

2. Binding

哪個 framework/decorator/fixture/dependency 將它綁到哪個 parameter？

3. Type

進入 function 前後型別有沒有從 JSON string 變 Decimal/model？

4. Sender → Receiver

誰呼叫誰？是 HTTP、Python call、SQL parameter、return，還是 Kafka record？

5. Transform

是否 validate、format、derive、hash、reserve、default、serialize？

6. Lifetime / Evidence

只在 memory？進 transaction？commit/rollback？哪個 test/SQL 證明？

一行版origin → binding → typed variable → handler transform → SQL/return → commit/rollback → downstream receiver → evidence
